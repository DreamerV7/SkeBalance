# СкеБаланс

Веб-прототип прогноза остатка до следующего дохода. Сценарий: импорт выписки → проверка расходов → прогноз → проверка покупки. Версия 0.2 добавляет аккаунты и сохранённые расчёты через Supabase.

## Возможности

- Импорт CSV и экспериментальный импорт одного текстового PDF-шаблона Сбера.
- Просмотр и исключение операций, поиск регулярных платежей с исправлением суммы и даты.
- Расчёт повседневных расходов, остатка, лимита покупки и запаса относительно резерва.
- Регистрация, подтверждение email, вход, восстановление и смена пароля.
- Сохранение, открытие и удаление своих расчётов.
- Миграция PostgreSQL с проверкой сохраняемых данных и Row Level Security.
- GitHub Actions для проверок, миграций и публикации на Netlify с ключами из Secrets.

Калькулятор работает без аккаунта. Для реальной регистрации необходимо подключить Supabase и применить миграцию. Наличие репозитория само по себе не создаёт таблицы и не настраивает отправку писем.

## Запуск

Требуется Node.js 22 или новее. Для приложения установка зависимостей не нужна: PDF.js и официальный Supabase JS 2.119.0 уже включены локально со своими лицензиями.

```powershell
node scripts/build.mjs
node server.mjs
```

Открыть http://127.0.0.1:4173. В Windows можно запустить start.cmd. Не открывать index.html через file://. Остановить сервер: Ctrl+C.

Без переменных сборка включает калькулятор без аккаунтов. Для подключения задать SUPABASE_URL и SUPABASE_PUBLISHABLE_KEY в окружении и повторить сборку. Пример имён — .env.example; скрипт не читает .env автоматически. В dist/config.js попадают только эти два публичных значения.

## Развёртывание

Пошаговая настройка: [docs/SETUP.md](docs/SETUP.md).

Выберите один способ публикации: GitHub Actions с ключами из GitHub Secrets либо встроенная сборка Netlify с настройками в Netlify. Не включайте оба: они будут перезаписывать публикации друг друга. Для базы тоже выбирается один механизм применения миграций.

В этой локальной сессии применение миграций к облачной БД, реальная регистрация и отправка писем не выполнялись. До получения параметров проекта они не считаются проверенными.

## Данные и доступ

Выписка и транзакции обрабатываются в браузере. Только нажатие «Сохранить в аккаунте» передаёт название, даты, суммы, ежедневную оценку и будущие платежи. В сохранении нет PDF, имени файла, полной истории, реквизитов и идентификаторов исходных операций.

Паролями управляет Supabase Auth; в прикладных таблицах паролей нет. Токены входа сохраняются в sessionStorage текущей вкладки, без исходной выписки. При выходе открытый расчёт и список сохранений очищаются.

Пользователь может читать, создавать и удалять только свои сохранения. Запись от имени другого пользователя и обновление владельца запрещены PostgreSQL-политиками и правами. Удаление аккаунта в Supabase каскадно удаляет его сохранения.

Publishable key виден в готовом сайте, даже если исходно хранится в GitHub Secrets. Защиту обеспечивают Auth и RLS. Secret key, service_role, пароль БД и токены управления в сайт не включаются. Сборка отклоняет секретный ключ вместо Publishable key.

## Расчёт

Период — от начала даты расчёта до начала дня следующего дохода. Сам доход не прибавляется. Для анализа истории используются только полные дни и операции строго до даты расчёта. Баланс вводится вручную: старый остаток выписки не считается актуальным.

Ежедневные расходы — сумма исторических списаний без исключённых операций и регулярных групп, делённая на число календарных дней полного периода. Среднее округляется до копейки и может быть заменено вручную.

Для регулярного кандидата нужны минимум три похожих списания с интервалами 25–35 дней; допускается один пропуск 55–65 дней. Суммы отличаются от медианы не более чем на 20%. Переводы не становятся регулярными автоматически. Сумма платежа — медиана; число и сумма редактируются. В коротком месяце для 31-го используется последний день.

Отключённый регулярный платёж не планируется на будущее; его история остаётся исключённой из среднего. Кнопка «Обычные траты» возвращает группу в среднее.

- Остаток до покупки = баланс − обязательные платежи − расходы в день × дни.
- Лимит покупки = max(0, остаток до покупки − резерв).
- Остаток после покупки = остаток до покупки − покупка.
- Запас относительно резерва = остаток после покупки − резерв.

Все внутренние суммы представлены целыми копейками. Платежи вне горизонта не вычитаются и отдельно перечисляются. Сохранённый расчёт содержит оценку ежедневных расходов, а не исходную историю. При его открытии результаты вычисляются заново; можно менять даты и суммы.

## Импорт

CSV: UTF-8 или Windows-1251, разделители ; , либо табуляция. Нужны дата и сумма либо дата, приход и расход. Дополнительные поля: категория, описание, остаток, тип, валюта. Отрицательная сумма означает списание; если есть столбец типа, направление берётся из него. Только RUB. Ошибочные строки останавливают импорт без молчаливого пропуска. Полный период CSV подтверждается вручную. Шаблон скачивается в интерфейсе.

PDF: экспериментальный текстовый шаблон «по счёту дебетовой карты» или «по платёжному счёту» с датой/временем, категорией, суммой и остатком. PDF.js восстанавливает строки по координатам. Если итоги распознаны, суммы поступлений и списаний сверяются с ними. Несовпадение и неоднозначные строки блокируют импорт. При отсутствии итогов требуется ручная сверка. Сканы, кредитные карты и валютные счета не поддержаны.

Лимиты: 15 МБ, 80 страниц PDF, 20 000 операций CSV. Импорт настоящей выписки пользователя ещё не проверен; совместимость со всеми шаблонами Сбера не заявляется.

## Проверки

```powershell
npm ci --ignore-scripts
npm test
npm run build
# При работающем локальном сервере:
npm run test:browser
```

23 проверки логики и PostgreSQL-политик проходят локально. Используется PostgreSQL-движок PGlite с ролями anon/authenticated, двумя пользователями и моделированием auth.uid. Политики исполняются, а не проверяются поиском текста SQL.

Браузерные проверки работают в Edge на Windows и Chromium в CI. Проверены калькулятор, импорт/экспорт, синтетический PDF, ошибки ввода, подтверждение истории, формы регистрации и входа, сохранение/открытие/удаление, выход и ширина 390 px. Для аккаунтов используется тестовый API без реальных ключей и отправки писем. Реальное подключение требует отдельной проверки по docs/SETUP.md.

## Ограничения

Точность на реальных расходах и полезность для участников пока не установлены. Нет банковского API, ML и автоматического определения резерва. Неполные данные, необычные покупки и задержка дохода влияют на результат. Это оценка при заданных условиях, а не гарантия безопасности покупки.

Следующий эксперимент: сверить импорт реальной обезличенной выписки, измерить ошибку на трёх периодах без использования будущих данных и отдельно проверить понятность и пользу у пяти участников.
